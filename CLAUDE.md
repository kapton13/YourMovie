# YourMovie — контекст проєкту

## Що будуємо
Трекер аніме (згодом також серіалів і фільмів) за логікою як myshows.me:
- багато користувачів, реєстрація через **пошту й пароль**;
- особисті списки: «Дивлюся», «Переглянуто», «Планую», «Кинув», оцінки 1–10, відмітки серій;
- каталог з **розширеними фільтрами**;
- рекомендації на основі оцінок і схожих тайтлів.

Мови сайту (рішення власника 2026-10-15): сайт інтернаціональний, мову додати легко; перші — англійська, українська, російська; з 2026-10-15 також іспанська, португальська, французька, німецька, польська, турецька, японська, корейська, китайська (12). За замовчуванням англійська, мову людина обирає сама (перемикач у шапці, зберігається в профілі); автовибору за браузером немає. Мова в адресі (`/en/...`). Спілкування з власником — українською.

## Ухвалені рішення
- **Дані про аніме:** AniList GraphQL API (`graphql.anilist.co`), без ключа. На сайті обов'язкове посилання на AniList як джерело.
- **Серіали й фільми (пізніше):** TMDB (`api.themoviedb.org`), потрібен безкоштовний ключ і згадка TMDB. Перед комерційним використанням перевірити умови AniList і TMDB.
- **Російські назви й описи аніме:** Shikimori API (`shikimori.io`, раніше `shikimori.one`), зіставлення через MAL id з AniList. Перевірити умови використання.
- **Акаунти й база користувачів (етап 2):** Supabase (Auth через email+пароль, Postgres).
- **Розміщення:** Vercel з автодеплоєм з гілки `main`. Підключено: https://your-movie-five.vercel.app
- **Платний ШІ-помічник (Claude API):** відкладено. Коли повернемося: запити йдуть через серверну функцію, ліміт запитів на користувача, дешева модель, кешування.
- **Стек:** Next.js 16 (App Router, TypeScript, Cache Components з `"use cache"`), звичайний CSS (CSS-модулі), без Tailwind. Запити до AniList — на сервері (`lib/anilist.ts`), кешуються на годину. Постери — звичайний `<img>` з `s4.anilist.co`.

## Етапи
1. **Каталог** (готово): головна (тренди, поточний сезон, популярне, топ рейтингу), пошук, фільтри (жанри включити/виключити, роки, сезон, формат, статус, кількість серій, мінімальний рейтинг, країна, сортування; стан фільтрів у URL), сторінка тайтлу (постер, опис, інфо, теги, пов'язані та схожі тайтли).
2. **Реєстрація та особисті списки (Supabase)** — готово. Статуси: Дивлюся / Планую / Переглянуто / На паузі / Кинув. Оцінки 1–10 (ряд цифр) для тайтлу й для кожної серії; оцінено всі серії сезону → оцінка сезону = їх середнє; оцінено всі основні сезони → оцінка аніме = середнє сезонів (середнє має перевагу над ручною, ручну тоді не змінити). Статус: оцінка «Переглянуто» не ставить (нове аніме → «Дивлюся»); «Переглянуто» само — коли відмічено всі серії, що вже вийшли, в усіх основних сезонах (навіть якщо аніме ще виходить — рішення власника 2026-10-15); вийшла нова/є невідмічена серія, що вже вийшла → «Дивлюся»; OVA/спешли не впливають. Детальний план — у `PROGRESS.md`.
3. **Рекомендації без ШІ** — готово (2026-10-14): сторінка «Рекомендації» з фільтрами, ряд «Для вас» на головній.
4. Профіль і статистика — готово (2026-10-14): `/u/<нікнейм>`, закритий за замовчуванням, перемикач у налаштуваннях. Далі — шліфування, мобільна версія; пізніше — TMDB, ШІ-помічник.

## Як працювати з власником проєкту
- Власник не програміст: пояснювати просто, спілкуватися **українською**.
- **Не поспішати створювати.** Великі речі спершу коротко обговорити й узгодити, потім робити.
- **Усі платні сервіси (домен, платні тарифи тощо) — на останній момент, перед запуском** (рішення власника 2026-10-18). Зараз — лише безкоштовне; готувати все так, щоб у день запуску лишилося тільки вставити налаштування.
- Якщо власник пише «стоп», одразу зупинитися і не надсилати в GitHub незавершену роботу.
- Технічну перевірку робить Claude сам (збірка, перегляд у браузері, десктоп і мобільний); власник оцінює лише, чи це те, чого він хотів.
- Працювати етапами; після кожного етапу сайт має бути робочим.
- Оновлювати цей файл, коли ухвалюються нові рішення або завершується етап.
- **Журнал прогресу — `PROGRESS.md`.** На початку кожної сесії спершу прочитати його. Після кожного завершеного кроку або нової домовленості оновити журнал і відправити в GitHub, щоб нічого не загубилося, якщо чат обірветься.

## Пошук і каталог (як влаштовано)
- Стан каталогу (пошук, фільтри, сортування, сторінка) — у `lib/catalog.ts`: читання/запис адреси (`parseCatalogParams`, `catalogHref`). Файл спільний для сервера й браузера.
- Запит до AniList з усіма фільтрами — `getCatalogPage` у `lib/anilist.ts` (по 48 на сторінку, кеш на годину). Для тегів `minimumTagRank: 40`.
- Ранжування за назвою — `lib/search.ts` (якість збігу + популярність). AniList не шукає за недописаним словом, тому є словник `data/title-index.json` (3000 популярних назв, включно з російськими синонімами) — `lib/titleIndex.ts`; він же дає підказки при одруківках.
- Панель фільтрів — клієнтський компонент `components/catalog/CatalogControls.tsx` (оптимістичне оновлення, введення з затримкою 400 мс).

## Акаунти (як влаштовано)
- Supabase: `lib/supabase/config.ts` (URL і publishable key — публічні; секретний ключ у код не класти ніколи), `client.ts` (браузер), `server.ts` (сервер), `remember.ts` («Залишатися в системі» через строк життя cookies).
- Вхід/реєстрація — у браузері (`components/auth/*`), сесія в cookies. Шапка показує стан через `useUser()`, тож сторінки лишаються статичними.
- Схема бази — у `supabase/*.sql` (власник запускає вручну в SQL Editor; файли безпечні для повторного запуску). Таблиці: `profiles` (нікнейм унікальний, будь-якою мовою, але літери однієї абетки — `NICKNAME_SCRIPTS` у `lib/profile.ts` = `nickname_valid` у `supabase/007_*.sql`, змінювати разом; «User»+цифри — лише автоматичні; прізвище, ім'я, по батькові — окремі поля до 50 символів, телефон, країна — приватні), `list_entries`, `episode_marks`; усюди RLS «лише свої записи».
- **Групування в одне аніме:** `getFranchise` у `lib/anilist.ts` (ланцюжок PREQUEL/SEQUEL = основні частини; SIDE_STORY/PARENT/SUMMARY = додаткові; спін-офи окремо; кеш на дні). Статус і оцінка аніме — у `list_entries` під `key` (id найпершої основної частини); відмітки серій — по частинах; оцінки сезонів — `season_scores`. Правила — `lib/franchiseRules.ts`.
- **«Не цікаво»:** хрестик на будь-якій частині ховає все аніме (усі сезони, фільми, OVA) скрізь — головна, каталог, пошук, схожі, рекомендації. Таблиця `hidden_media` (id кожної частини + `franchise_key`), `components/hidden/HiddenProvider.tsx` (у layout): одразу ховає частину й першу частину (`rootId`), потім зберігає всі частини; при кожному відкритті сайту доповнює неповні записи й нові сезони. Картки ховаються через `Hideable` (за id, `rootId` або `parentId` — попередня частина; у каталозі `parentId` приходить тим самим запитом). Спін-офи (окремі аніме) не ховаються. Рекомендації мають їх виключати.
- **Вже в списках:** аніме зі статусами «Дивлюся», «Переглянуто», «На паузі», «Кинув» (усі частини) не показуються на головній, у «Схожих» і рекомендаціях (`SkipListed`, `listedIds` у `HiddenProvider`; картки мають `rootId` — першу частину аніме з `getRoots`, тож сезон 3 ховається, навіть якщо `/api/franchises` не встиг). «Планую» показуємо. Каталог і пошук показують усе.
- Вбудована пошта Supabase надсилає листи лише учасникам проєкту → для людей потрібен свій SMTP (домен + Resend тощо) — **перед запуском** (платне відкладено).
- **Листи:** тексти — `messages/<мова>/email.ts`; шаблони для Supabase генерує `npm run email-templates` (`lib/emailTemplates.ts` → `supabase/email-templates/*.html`, Go-шаблон з гілкою на кожну мову за `user_metadata.language`; змінив тексти — перегенерувати, тест стежить). Посилання — `token_hash` на `/auth/callback` (працює на будь-якому пристрої). Мову в `user_metadata` пишуть реєстрація й `useSwitchLanguage`.
- **Захист від зловживань:** `lib/rateLimit.ts` (межа на IP, на серверний процес) — API-маршрути й пошук у `proxy.ts`. Нові дорогі маршрути — теж через `LIMITS`.
- **Бережемо AniList** (домовленість 2026-10-21): усі запити — лише через `anilist()` у `lib/anilistClient.ts`: ≤ 3 одночасно (черга), однакові одночасні запити — один, 403 (AniList вимкнув API) — 5 хв не звертаємось, 3 збої поспіль — 1 хв пауза, 429 — чекаємо Retry-After (довго — відмовляємо одразу), лишився 1 запит у хвилині — чекаємо поновлення; таймаут 15 с; `ANILIST_DEBUG=1` друкує кожен запит. Пам'ять по кожному аніме (`franchiseMemo` за будь-якою частиною, `myMediaMemo` 5 хв, `previousMemo`, `seedMemo`/`cardMemo`) — спільна на процес через `shared()` (`lib/shared.ts`; Next має окремі копії модулів для сторінок і API). Збирання сайту не залежить від AniList: `failedDuringBuild` робить дані «дірою» для сервера (головна, фільтри каталогу, `getRoots`); такі дані на сторінці — лише всередині `<Suspense>`.

## Копія даних AniList (як влаштовано, домовленість 2026-10-21)
- Таблиця `anime_store` (SQL `010`; `kind` = `franchise` / `part` / `media` / `details` / `episodes`, `data` jsonb). Читають усі (публічний ключ), **пише лише нічний робот** `scripts/sync-anime-store.mts` (`npm run sync-store`, `.github/workflows/anime-store.yml`, секрет `SUPABASE_SECRET_KEY` — тільки в GitHub, ніколи у Vercel/коді/чаті).
- Сайт: `lib/animeStore.ts` (`readStore`, не кидає помилок; таблиці немає — 10 хв не питає). Групування аніме — з копії, якщо робот оновив його ≤ 8 днів тому (інакше AniList, а при збої — давня копія); картки «Моїх аніме», сторінка аніме, серії — з AniList, а коли AniList не відповідає — з копії (`refreshAired` / перерахунок «вийшла» за датами).
- Робот щоночі (≤ 55 хв): аніме зі списків — групування раз на тиждень, картки щодня, сторінки раз на тиждень, серії (що виходить — щодня); потім групування 1000 найпопулярніших (раз на місяць кожне). AniList вимкнений (403) — зупиняється.
- Функції без кешу Next для робота: `buildFranchise`, `fetchMediaDetails`, `buildEpisodes`, `getMyMediaChunk` (кешовані обгортки — `getFranchise`, `getMedia`, `getEpisodes`, `getMyMedia`).
- Кросовер (спешл чи фільм, що є побічною історією двох аніме, як «Lupin III vs Meitantei Conan») не зливає аніме: з частини, до якої дійшли, «побічні» зв'язки до нових серіалів не ведуть (`buildFranchise`; перевірено на 40 популярних — змінились лише Конан/Люпен).

## Нові серії (як влаштовано)
- Правило «нова серія» — `lib/newEpisodes.ts` (невідмічена серія, що вийшла за останні 7 днів, у сезоні або в уже початій побічній частині); його використовують «Мої аніме» (позначка «Нова серія!») і кружечок у шапці (`useNewEpisodes` у `MyAnimeLink`: «Дивлюся» + «Переглянуто», пам'ять вкладки 10 хв). Хто змінює списки — викликає `notifyListsChanged()` (уже в `UserMediaProvider` і «Моїх аніме»).

## Рекомендації (як влаштовано)
- `lib/recommendations.ts`: вага кожного аніме зі списку (`seedWeight`: оцінка 9–10 сильно «за», 1–4 «проти», «Дивлюся» трохи важить більше, «Кинув» — м'яко «проти», «Планую» — 0); кандидати — «схожі» AniList (`getRecSeeds`, по 25 аніме за запит, пам'ять сервера 6 год); смак за жанрами й тегами; продовження → перша частина (`getRecCards`); мало даних — доповнюємо популярним; «чому порадили» в `reason`.
- Аніме зі списків (крім «Планую») сервер виключає **всіма частинами за `getFranchises`** (те саме групування, що «Мої аніме»; паралельно, ≤ 4 с), бо ланцюжок «попередніх частин» не бачить передісторій, що вийшли пізніше (Fate/Zero); «Не цікаво» браузер надсилає всіма частинами; браузер додатково відсіює за `listedIds`/`hiddenIds`.
- AniList іноді відмовляє серверам Vercel: рекомендації будуються з того, що прийшло (`inChunks` не валить решту, `attempt` у `buildRecommendations`), помилка — лише коли не прийшло нічого; браузер сам пробує ще раз, далі кнопка. Помилки `/api/*` містять відповідь AniList (`lib/apiError.ts`).
- `/api/recommendations` (POST): браузер читає свої списки й надсилає лише id, статуси, оцінки й сховані id. Клієнт — `components/recs/*` (`useRecommendations` з пам'яттю між сторінками, `Recommendations` — сторінка з фільтрами, `ForYouRow` — ряд на головній).
## Профіль (як влаштовано)
- `/u/<нікнейм>` — `components/profile/ProfileView.tsx` (браузер читає `profile_by_nickname`, списки й відмітки; дані AniList — `/api/my-media`), статистика — `lib/stats.ts`.
- Відкритий профіль (`profiles.is_public`, SQL `008`): списки, відмітки й оцінки сезонів читаються всіма; «Не цікаво», ПІБ, телефон, країна, пошта — ніколи. **Тому кожен запит своїх списків має `.eq("user_id", user.id)`**, а великі вибірки — через `selectAll` (ліміт 1000 рядків).

## Мови (як влаштовано)
- Мови — `lib/i18n/config.ts` (`LOCALES`, `LOCALE_INFO`: назва, код для Intl, напрям письма). Сторінки — під `app/[lang]/…`; `proxy.ts` додає мову до адрес без неї (з cookie `ym-lang` або англійську).
- Тексти — словники `messages/<мова>/<розділ>.ts` (common, labels, home, catalog, anime, list, my, hidden, recs, profile, auth, account). Англійський — зразок і запасний; `uk`/`ru` типізовані `Messages[...]` і мусять бути повні; нова мова може бути неповною (чого бракує — англійською).
- **Додати мову:** скопіювати `messages/en/` у `messages/<код>/`, перекласти, зареєструвати в `messages/index.ts` і в `LOCALES`/`LOCALE_INFO` (для мов справа наліво — `dir: "rtl"` і перевірити верстку).
- У компонентах: клієнтські — `useI18n()` (`m`, `fmt`, `count`, `intl`, `href`), `Link` і `useLocaleRouter()` з `components/i18n/I18nProvider`; серверні — `await getI18n()` з `lib/i18n/server`. Ніякого тексту в коді, дати й числа — через `Intl` з `intl`, множина — `count(m.common.episodes, n)`. Підписи частин аніме — `partLabel(part, m)`.
- Назви аніме мовою: `animeTitle(title, lang)` з `lib/i18n/title.ts`. Російські назви — словник `data/ru-titles.json` (≈5000 найпопулярніших, з Shikimori; `npm run update-ru-titles`), його підставляє `attachRussianTitles` в усі відповіді AniList (`title.russian`). На сторінці аніме для `ru` — назва й опис напряму з Shikimori (`lib/shikimori.ts`, кеш на дні) з посиланням на джерело; в підвалі російської версії — згадка Shikimori. Японською — оригінальні назви (`title.native`). Інші мови — назви англійською; описи всіх мов, крім російської, — англійською (AniList).
- Теги: `m.tags[назва]` (`messages/<мова>/tags.ts`; англійською — як є).
- Блоки, що приходять пізніше за спільний стан (користувач, списки, «Не цікаво»), спершу мусять показати те саме, що сервер: `useHydrated()` (`components/useHydrated.ts`), уже вбудовано в `useUserMedia` і `useHidden`.
- Вибір мови: перемикач у шапці й «Мова сайту» в налаштуваннях (`useSwitchLanguage`), зберігається в cookie і `profiles.language` (SQL `009`), мова профілю діє на всіх пристроях. **Обрана мова має перевагу над мовою в адресі** (рішення 2026-10-18): `proxy.ts` (`languageRedirect`) одразу відкриває сторінку мовою з cookie; хто не обирав — бачить мову з адреси. Зміна мови — повне перезавантаження (`reloadIn`), не клієнтський перехід; після входу — одразу на мову профілю; на сторінках входу мова профілю не підхоплюється (`isAuthPage`).

## Автоматичні перевірки (домовленість з власником 2026-10-15)
- **`npm run check`** — перевірка коду, типів і швидкі перевірки (`tests/unit`, ≈2 с, без мережі). **Запускати перед кожною відправкою в GitHub.**
- **`npm run test:e2e`** — повні перевірки в браузері (`tests/e2e`, ≈5–6 хв): усі 12 мов гостем (комп'ютер і телефон, без помилок і неперекладеного тексту), правила статусів, «Не цікаво», профіль, мова профілю. Потрібні: зібраний сайт (`npm run build`, у цьому середовищі з `NODE_USE_ENV_PROXY=1`) і тестовий акаунт у `.env.e2e.local` (`E2E_EMAIL=…`, `E2E_PASSWORD=…`; файл у git не потрапляє; лише тестовий акаунт — тести змінюють списки й повертають як було). **Запускати перед кожним об'єднанням з `main`.**
- **Кожне нове правило, про яке домовились, одразу отримує перевірку** (швидку — для логіки в `lib/`, повну — для поведінки на сторінці). Логіку тримати в `lib/` (чисті функції: `franchiseRules`, `hidden`, `stats`…), щоб її можна було перевірити окремо.
- Що вже перевіряється: правила статусів і оцінок (`franchiseRules.test.ts`), «Не цікаво» (`hidden.test.ts`), нікнейми/імена/`safeNext` і збіг абеток із базою (`profile.test.ts`), фільтри каталогу й пошук (`catalog.test.ts`), повнота всіх 12 словників, форми множини, місця для значень, теги, однакові назви статусів (`i18n.test.ts`), статистика й вага рекомендацій (`stats-recs.test.ts`), рекомендації при збоях AniList і без аніме зі списків (`recommendations.test.ts`), черга/пауза/повтори запитів до AniList (`anilistClient.test.ts`), групування й кросовери (`franchise.test.ts`), копія даних (`animeStore.test.ts`).

## Роботи GitHub (домовленість з власником 2026-10-21)
- `.github/workflows/check.yml` — швидкі перевірки на кожну зміну.
- `site-health.yml` — щогодини перевіряє живий сайт і AniList (`scripts/site-health.mjs`; ознака даних — постери `s4.anilist.co`, бо текст помилки є в словнику кожної сторінки). Біда — задача з міткою `site-health` (лист власнику), минула — закриває; AniList повернувся — запускає `e2e` для pull request з міткою `merge-when-green`.
- `e2e.yml` — повні перевірки в браузері на GitHub (вручну з номером pull request або міткою `merge-when-green`; з міткою після успіху сам зливає, якщо голова не змінилась). Секрети `E2E_EMAIL`/`E2E_PASSWORD` — окремий тестовий акаунт (власник вписує сам у Settings → Secrets; у чат не надсилати). AniList не відповідає — відкладає.
- `anime-store.yml` — щоночі оновлює копію даних AniList (див. «Копія даних AniList»); без секрету `SUPABASE_SECRET_KEY` пропускає.
- `update-dictionaries.yml` — щопонеділка оновлює `data/title-index.json` і `data/ru-titles.json` (скрипти чекають 2,1 с між запитами до AniList і не пишуть словник, якщо даних помітно менше), проганяє `npm run check` і пропонує зміни з гілки `bot/dictionaries`.
- `check.yml`, завдання `build` — збирає сайт і міряє вагу коду для браузера (`npm run budget`, межі — `bundle-budget.json`; стало важче — помилка; свідомо — підняти межу).
- `.github/dependabot.yml` — щотижня один pull request з дрібними оновленнями бібліотек; великі — окремо, обговорюємо.
- Розклад (`schedule`) працює лише з `main`.

## Команди
- `npm run dev` — локальний запуск; `npm run build` — збірка; `npm run budget` — вага коду для браузера (після збірки); `npm run lint` — перевірка коду; `npm run check` і `npm run test:e2e` — див. «Автоматичні перевірки».
- `npm run update-titles` — оновити словник назв для пошуку (≈2 хв, запити до AniList).
- `npm run update-ru-titles` — оновити російські назви з Shikimori (≈5 хв).
